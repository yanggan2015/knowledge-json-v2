# VFS 打开路径：从 path_openat 到 inode->i_fop 的统一抽象

`open` 返回奇怪 errno、海量小文件把内存打满、`O_DIRECT` 对齐失败：这些往往出在 **VFS 的路径查找与对象模型**（dentry/inode/file），而不是某一个具体 FS 的业务逻辑。本文沿 **`path_openat` → `lookup` → `vfs_open` → `f_op`** 走通打开与读写交接，便于对照 `strace` 与缓存压力排障。

## 源码锚点

| 路径 | 作用 |
|------|------|
| `fs/namei.c` | 路径名查找、`path_openat`、`link_path_walk` |
| `fs/open.c` | `do_sys_open` / `vfs_open` 等打开路径 |
| `fs/read_write.c` | `vfs_read` / `vfs_write` |
| `include/linux/fs.h` | `struct inode`、`struct file`、`file_operations` |
| `include/linux/dcache.h` | `struct dentry`、dcache |
| `fs/dcache.c` | dentry 缓存、negative dentry |
| `Documentation/filesystems/vfs.rst` | VFS 方法表总览 |

核心对象（头文件）：

```c
/* include/linux/fs.h — 打开后用户态 fd 对应的内核对象 */
struct file {
	const struct file_operations *f_op;
	struct inode *f_inode;   /* 关系随版本以源码为准 */
	void *private_data;
	loff_t f_pos;
	/* … */
};

struct file_operations {
	struct module *owner;
	ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
	ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
	int (*open)(struct inode *, struct file *);
	/* … */
};
```

路径查找与打开（逻辑骨架）：

```c
/* 用户态 open → 系统调用 → fs/namei.c / fs/open.c */
path_openat(...)
  → 逐组件 lookup（dcache 命中或 inode->i_op->lookup）
  → 权限检查（inode_permission 等）
  → vfs_open → 绑定 file->f_op = inode->i_fop
  → 若 f_op->open 存在则调用
```

## 调用链

```text
openat(dfd, path, flags)
  → do_sys_open / do_filp_open
      → path_openat                    /* fs/namei.c */
          → link_path_walk             /* 逐级 dentry */
              → lookup_fast（dcache）或 lookup_slow（→ i_op->lookup）
          → 处理 O_CREAT / O_TRUNC / 尾随斜线等标志
          → vfs_open
              → file->f_op = fops_get(inode->i_fop)
              → f_op->open(inode, file)   /* 具体 FS 或字符/块设备 fops */

read(fd, …)
  → vfs_read
      → file->f_op->read 或 read_iter
          → 常见：generic_file_read_iter → page cache → read_folio/get_block
```

缓存协作：

```text
dentry 缓存加速路径组件
inode 持有元数据与 i_mapping（地址空间）
page cache 命中则少读盘；miss 则经 mapping → FS → 块层
```

## 重点知识

**1. VFS 四件套分工要清楚**  
- **dentry**：路径组件缓存（含 negative dentry「不存在」）。  
- **inode**：元数据与操作表（`i_op`/`i_fop`）。  
- **file**：一次打开的会话（位置、模式、`private_data`）。  
- **super_block**：一个挂载实例的 FS 全局状态。  
排障时先分清是「路径找不到」（dentry/权限）还是「打开后读写失败」（f_op/块层）。

**2. `file->f_op` 在 open 时钉死**  
后续 `read`/`ioctl` 都走这张表。设备文件会在字符/块层替换 fops（如 `chrdev_open`）；普通文件则是具体 FS 的 `file_operations`。混用错误的挂载选项或错误的 inode 类型，会进错操作集。

**3. dcache 与内存压力**  
海量小文件遍历会堆 dentry/inode；`vm.vfs_cache_pressure` 影响回收积极性。negative dentry 能加速「反复查不存在的路径」，也可能在错误场景下掩盖刚创建的文件（少见，多与并发创建有关），需结合业务理解。

**4. 观测命令**

```bash
strace -e openat,open,stat,read,write cat /path/to/file
mount | grep <mp>
cat /proc/sys/vm/vfs_cache_pressure
# 页缓存与回写粗看
cat /proc/meminfo | grep -E 'Cached|Dirty|Writeback'
iostat -x 1
# 权限与挂载项
findmnt -T /path/to/file
```

**5. 设计意图与踩坑**  
- **意图**：用统一对象模型让 ext4/XFS/NFS/proc 共享系统调用入口。  
- **坑**：数据库目录未 `noatime`，atime 更新放大写。  
- **坑**：`O_DIRECT` 缓冲/偏移未按逻辑块对齐 → `EINVAL`。  
- **坑**：容器 overlay 上层小文件写放大，误判为「磁盘慢」。  
- **坑**：只看 FS 调优，忽略 VFS 权限、挂载 flags（`ro`/`nodev`/`nosuid`）。
