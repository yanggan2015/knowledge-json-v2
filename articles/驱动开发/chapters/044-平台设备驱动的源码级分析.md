# platform 驱动匹配：从 platform_driver_register 到 probe 的 DT 绑定

板级外设「有节点无驱动」或 probe 从未进：多半卡在 **总线匹配**，不是业务代码。本文沿 **`platform_driver_register` → `platform_match` → `really_probe` → 驱动 `probe`** 走通 SoC 片上设备绑定，对照设备树 `compatible` 与 `of_match_table` 排查。

## 源码锚点

| 路径 | 作用 |
|------|------|
| `include/linux/platform_device.h` | `platform_device` / `platform_driver` / `platform_device_id` |
| `drivers/base/platform.c` | `platform_driver_register`、`platform_match`、`platform_probe` |
| `drivers/base/dd.c` | `device_attach`、`really_probe`、驱动绑定核心 |
| `drivers/of/device.c` | `of_driver_match_device`、`of_match_device` |
| `Documentation/driver-api/driver-model/platform.rst` | platform 总线说明 |

结构骨架：

```c
/* include/linux/platform_device.h */
struct platform_driver {
	int (*probe)(struct platform_device *);
	void (*remove)(struct platform_device *);
	struct device_driver driver;
	const struct platform_device_id *id_table;
};

struct platform_device {
	const char	*name;
	int		id;
	struct device	dev;
	u32		num_resources;
	struct resource	*resource;
};
```

注册入口（概念）：

```c
/* drivers/base/platform.c */
int platform_driver_register(struct platform_driver *drv)
{
	drv->driver.bus = &platform_bus_type;
	return driver_register(&drv->driver);
}
```

## 调用链

```text
module_init / platform_driver_register(pdrv)
  → driver_register(&pdrv->driver)
      → bus_add_driver
          → driver_attach
              → 遍历 platform_bus 上已有 device
                  → platform_match(dev, drv)
                      → of_driver_match_device   /* DT compatible */
                      || ACPI / id_table / name 匹配
                  → really_probe (dd.c)
                      → platform_probe
                          → pdrv->probe(pdev)
```

设备侧（设备树先于驱动加载时）：

```text
of_platform_populate / platform_device_add
  → device_add
      → bus_probe_device
          → 同样进入 platform_match → probe
```

匹配优先级在 `platform_match` 内大致为：OF → ACPI → `id_table` → `name` 字符串。嵌入式 SoC 几乎全走 **OF `compatible`**。

## 重点知识

**1. 匹配靠表，不靠「同目录」**  
`probe` 被调用的前提是 `platform_match` 成功。DT 节点写 `compatible = "vendor,foo"`，驱动必须在 `driver.of_match_table`（或等价 `of_match_ptr`）里有同一字符串；只改 `.name` 而不填 `of_match_table`，在现代内核上经常 **永远不匹配**。

**2. `platform_device` 携带资源，不承载协议**  
IRQ、MMIO、DMA 通道等来自 `pdev->resource` / `platform_get_resource` / `platform_get_irq`，或 DT 解析（`of_iomap`、`irq_of_parse_and_map`）。platform 总线本身不做传输协议——那是 I2C/SPI/USB 子系统的事；片上「没有标准总线」的外设才挂 platform。

**3. `really_probe` 失败要看返回值语义**  
`probe` 返回 `-EPROBE_DEFER` 时，内核会推迟再试（依赖时钟/regulator/GPIO 尚未就绪）。返回其他负值则绑定失败，设备可能停在「有驱动候选但未绑定」。排障先看 `dmesg` 里 defer 与 `-ENODEV`。

**4. 配置与观测**

```bash
# 设备与驱动是否绑定
ls -l /sys/bus/platform/devices/
ls -l /sys/bus/platform/drivers/<your_drv>/
# 未绑定设备常见：driver 链为空
readlink /sys/bus/platform/devices/<dev>/driver
# DT 与 compatible
cat /proc/device-tree/.../compatible   # 或 ls /sys/firmware/devicetree/base
# 推迟探针
cat /sys/kernel/debug/devices_deferred  # 需 debugfs
dmesg | grep -iE 'probe|defer|platform'
```

Kconfig 侧：驱动需编进内核或 `insmod`；对应 `CONFIG_*` 未开等于驱动根本不存在。

**5. 设计意图与踩坑**  
- **意图**：把「板级差异」收敛到 DT/ACPI，驱动只认 compatible + 资源。  
- **坑**：`compatible` 拼写与驱动表不一致（多一个厂商前缀、大小写）。  
- **坑**：资源索引写死 `platform_get_resource(pdev, IORESOURCE_MEM, 0)`，DT `reg` 顺序变了就映错地址。  
- **坑**：在 `probe` 里假设全局单例设备，忽略同一 `compatible` 多实例（多 UART）。  
- **坑**：`remove`/`devm_` 生命周期不一致导致卸载后 UAF。

## Checklist

- [ ] 能指出 `platform_driver_register` → `platform_match` → `really_probe` → `probe` 的文件位置
- [ ] 确认驱动 `of_match_table` 与 DT `compatible` 字符串逐字一致
- [ ] 用 `sysfs` 看 `devices/.../driver` 是否已绑定；未绑定先查 match 而非业务逻辑
- [ ] `probe` 依赖时钟/电源时正确处理 `-EPROBE_DEFER`，并能查 `devices_deferred`
- [ ] 用 `platform_get_resource` / `platform_get_irq`（或 DT API）取资源，不硬编码物理地址
- [ ] 多实例设备用 `pdev` / `dev` 做私有数据，避免全局静态状态
